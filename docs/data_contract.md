# Data Contract

この文書は、Boatrace-AI-MVP におけるデータの命名・時系列・保存責務を固定するための契約である。

目的は次の 3 点。
- `race_id` の意味を一意にする
- `snapshot_time` と `data_phase` を曖昧にしない
- `raw` / `staging` / `processed` の責務を分離する

## 1. 基本キーの定義

### race_date
- 型: `YYYY-MM-DD`
- 意味: レース開催日を表す日付
- 例: `2026-04-20`

### jcd
- 型: string
- 意味: 開催場を表す JCD コード
- 備考: 施設名ではなく、機械処理可能な場コードを優先する
- 例: `12`

### rno
- 型: int
- 意味: レース番号
- 取りうる値: `1` 〜 `12`
- 例: `7`

### race_id
- 型: string
- 意味: `race_date` + `jcd` + `rno` を結合した一意キー
- 標準形式: `YYYY-MM-DD_JCD_RR`
- 例: `2026-04-20_12_07`
- 補足:
  - `race_id` はレース単位の主キーとして扱う
  - 同一レースの複数スナップショットや複数段階データでも `race_id` は変えない

## 2. 時点の定義

### snapshot_time
- 型: datetime
- 意味: そのレコードが「どの時点の情報」を表すかを示す観測時刻
- ルール:
  - 予測に使える情報は `snapshot_time` 以前に確定しているものだけ
  - `snapshot_time` より後に公開された情報を特徴量として混ぜない
- 例:
  - 出走表取得時刻
  - 直前オッズ取得時刻
  - 結果確定後の取得時刻

### data_phase
- 型: string
- 意味: そのデータがレースライフサイクルのどの段階に属するかを示す分類
- 取りうる値:
  - `entry`
  - `pre_race`
  - `final_odds`
  - `result`

#### entry
- 意味: 出走登録・番組確定前後に取得できる基礎情報
- 主な内容:
  - 選手情報
  - 級別
  - 全国勝率
  - モーター / ボート情報
  - 開催日・場・R 番号
- 利用目的:
  - 事前特徴量
  - 学習用の静的特徴量

#### pre_race
- 意味: 締切前の直前情報
- 主な内容:
  - 展示タイム
  - 気象
  - 直前の進入や気配
  - 直前に取得できる補助情報
- 利用目的:
  - 予想時点の特徴量
  - 終了前の最終判定

#### final_odds
- 意味: 締切直前または締切時点で確定したオッズ情報
- 主な内容:
  - 単勝 / 2連単 / 3連単などの確定オッズ
  - 期待値計算用の最終オッズ
- 利用目的:
  - EV 計算
  - BUY/WATCH/SKIP 判定

#### result
- 意味: レース終了後に確定した結果データ
- 主な内容:
  - 着順
  - 払戻
  - 的中フラグ
  - 評価指標
- 利用目的:
  - 回収率集計
  - バックテスト
  - 学習ラベル生成

## 3. データ層の責務

### raw
- 役割: 取得したままの原本を保存する層
- 原則:
  - 変換しない
  - 補完しない
  - 意味を足しすぎない
- 責務:
  - 元サイトから取れた事実を残す
  - 監査や再パースの起点にする
- 入力例:
  - 公式サイト HTML
  - 取得直後の CSV / JSON
- 出力例:
  - `raw/B/...`
  - `raw/K/...`
  - `raw/fan/...`

### staging
- 役割: raw を解析し、スキーマを揃える中間層
- 原則:
  - カラム名を正規化する
  - 型変換を行う
  - 文字列から数値や日付を分解する
  - ただし派生特徴量は最小限にとどめる
- 責務:
  - パースエラーの切り分け
  - 欠損や異常値の確認
  - raw と processed の橋渡し
- 入力例:
  - `data/raw/...`
  - `data/interim/...`
- 出力例:
  - 解析済みレース表
  - 正規化済みオッズ表
  - 検証用の中間 CSV

### processed
- 役割: 学習・推論・評価に直接使う確定済みデータ層
- 原則:
  - `race_id` を主キーとして整列する
  - 時系列の利用可能性を守る
  - 特徴量とラベルを分離する
- 責務:
  - モデル学習入力
  - 推論入力
  - バックテスト入力
  - 評価レポートの元データ
- 入力例:
  - staging で正規化済みのレースデータ
  - 過去結果を結合した学習テーブル
- 出力例:
  - `data/processed/historical_races.csv`
  - `data/processed/train_*`
  - `data/model_outputs/*`

## 4. ディレクトリごとの入出力例

### raw/
- 入力例:
  - 公式取得 HTML
  - ダウンロード直後の CSV
- 出力例:
  - パース前の原本ファイル
  - 日付・場単位の保存ファイル

### data/raw/
- 入力例:
  - `20260420_B12.html`
  - `20260420_K07.csv`
- 出力例:
  - 取得時のままの保存物

### data/interim/
- 入力例:
  - raw からのパース結果
  - 一時的な結合用 CSV
- 出力例:
  - カラム整形済みの中間ファイル
  - 不要列をまだ残した検査用ファイル

### data/processed/
- 入力例:
  - staging で整形済みのレース表
  - 未来情報を除いた学習用データ
- 出力例:
  - `historical_races.csv`
  - `train_win_proba.csv`
  - `train_place2_proba.csv`
  - バックテスト用スナップショット

### data/model_outputs/
- 入力例:
  - processed から作った推論対象レース
- 出力例:
  - `train_win_proba.csv`
  - 予測スコア付き CSV
  - モデル出力の集計結果

### data/strategy_outputs/
- 入力例:
  - model_outputs と odds の結合結果
- 出力例:
  - BUY/WATCH/SKIP 判定結果
  - 候補別 EV 集計

## 5. ルール

- `race_id` は全層で同じ意味にする
- `snapshot_time` は「その行が観測された時点」を示す
- `data_phase` は「その行がレースのどの段階に属するか」を示す
- `processed` には raw の再現不能な解釈を混ぜない
- 未来の `final_odds` や `result` を `entry` / `pre_race` に混ぜない

## 6. 未確定点

- `jcd` の正式な文字体系を `2桁固定` にするか `施設名併記` にするか
- `snapshot_time` を JST 固定にするか UTC で保存して表示時に変換するか
- `data_phase` の境界を、締切時刻基準にするか、データ取得完了時刻基準にするか
- `raw` と `staging` の境界を、現行の `data/raw` / `data/interim` に完全一致させるか
